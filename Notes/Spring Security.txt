The flow - 

The Controller/Service: You receive the JSON payload (UserID and Password).

The Manual Trigger: You call authenticationManager.authenticate().

The Registry: Because you defined authenticationProvider as a @Bean, Spring's internal configuration (typically in your SecurityConfig) has already injected that provider into your AuthenticationManager.

The Validation: The manager delegates the work to your DaoAuthenticationProvider. It uses your BCryptPasswordEncoder to verify the credentials.

The Success: Once verified, the manager returns a fully populated Authentication object.

The JWT Generation: Your code then takes over again, ignoring the session/cookie logic and instead passing the user details to your jwtService.generateToken().

--------------------------*****-----------------------------------------------------------------------------------

1. The JWT Service (The Toolkit)
Think of this as a utility box. It doesn't "do" anything on its own; it waits for the Filter to call its methods.

Generate: "Here is a username, give me a signed string."

Extract: "Here is a string, tell me what username is hidden inside."

Validate: "Does this string match this user, and is the clock still running (not expired)?"

--------------------------*****-----------------------------------------------------------------------------------


2. The JWT Filter (The Process)
This is the active worker that runs on every request. It follows this logic:

Check the Header: It looks for the Authorization: Bearer <token> header.

Call the Service: It passes the token to jwtService.extractUserName().

Check the "Guest List": Since it now has a username, it calls your UserDetailsService (the database) to get the full UserDetails (roles, permissions, etc.).

Final Verification: It asks the Service: "Does this token actually belong to this user I just found in the DB?"

Set the Context: If everything is perfect, it tells Spring Security: "This user is officially logged in for this specific request."
